# A corrected hub title renames nothing

A hub's file name is its title as an ASCII slug, and that slug is the prefix of
every child's file name. A commanded title correction therefore breaks the
agreement between title and file name for the hub and for every note under it.
The hub contract prescribed the correction and said nothing about the names, so
three readings were open at once: change the title only, refuse until the rename
is commanded with it, or rename everything.

The rule is now the one a note's title correction already had. Say in one line
what the hub and every child should be called, and leave the renames to me.

## Considered Options

**The agent renames the hub and its children (rejected).** It is the only option
that leaves nothing for me to do. It was rejected because it is `mv`, which step
2 of the same file forbids on a note: `mv` leaves the incoming wiki links
pointing nowhere on four devices, where a rename in Obsidian carries them along.
The child count makes that worse rather than better, and a hub is the one file
every child links to.

**Refusing the title correction until the rename is commanded with it
(rejected).** It never leaves a hub whose file name disagrees with its title. It
was rejected because it makes the cheap half wait on the expensive one, and
because the note's title correction already accepts exactly that mismatch as the
cheaper of the two errors.

## Consequences

- A hub can sit with a title its file name no longer matches, for as long as I
  leave it that way.
- The line falls again in a later session, because nothing records that it was
  already said, the same as the note's.
